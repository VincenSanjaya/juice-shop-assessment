Web Application Security Testing Methodology

Objective

The objective of this assessment was to identify common web application vulnerabilities in OWASP Juice Shop, validate their impact, and document appropriate remediation steps.

Testing Environment

Target: OWASP Juice Shop

Deployment: Local Docker container

Platform: macOS

Tools:
Burp Suite Community Edition
Chromium
Docker
Git

Scope

Testing was limited to the locally hosted OWASP Juice Shop instance.

Target URL:

http://localhost:3000

No external systems or third-party services were included in the assessment.

Testing Approach

Reconnaissance

The application was explored manually to identify available functionality, endpoints, forms, authentication flows, and user-controlled input.

Burp Suite HTTP History was used to observe requests generated by the application.

Request Interception and Analysis

HTTP requests were captured using Burp Suite Proxy.

Requests of interest were sent to Burp Repeater for manual modification and testing.

Testing focused on:

Request methods
Parameters
JSON request bodies
Object identifiers
Authentication headers
Application responses

Injection Testing

User-controlled parameters were tested for unsafe server-side processing.

The login functionality was tested using malformed input and SQL Injection payloads.

Response behavior, status codes, database errors, and authentication results were analyzed.

Cross-Site Scripting Testing

Application input fields were tested to determine whether user-controlled HTML was safely encoded.

HTML input was tested first.

JavaScript execution was then validated using a controlled XSS payload.

Access Control Testing

Authenticated functionality was tested using multiple resource identifiers.

Requests were modified to determine whether one authenticated user could access resources belonging to another user.

The basket endpoint was tested by modifying the basket ID.

Authentication Testing

The authentication and registration functionality was reviewed for weaknesses.

Testing included:

Login error comparison
Password policy validation
Client-side validation bypass
Direct modification of registration requests

Information Disclosure Testing

Application endpoints and publicly accessible directories were reviewed for exposed internal information.

The /ftp/ directory was inspected for publicly accessible internal files.

Evidence Collection

Screenshots were collected for confirmed findings.

Evidence included:

Modified HTTP requests
Server responses
Successful exploitation results
Exposed resources

Authentication tokens were redacted before publication.

Impact Analysis

Each confirmed vulnerability was evaluated based on the security impact demonstrated during testing.

The assessment considered:

Unauthorized access
Authentication bypass
JavaScript execution
Weak account security
Exposure of internal information

Remediation Analysis

Each finding includes remediation recommendations based on the identified root cause.

The goal was to describe how the vulnerability could be prevented rather than only documenting exploitation.

Testing Limitations

The assessment focused on selected common vulnerabilities and was not intended to represent a complete penetration test.

Automated vulnerability scanning, source code review, infrastructure testing, and extensive business logic testing were outside the scope of this project.
